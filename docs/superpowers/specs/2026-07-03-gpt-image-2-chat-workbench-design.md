# GPT Image-2 对话式图像工作台设计文档

## 1. 目标

在现有 Vue 3 + JS + Sass + Naive UI 项目基础上，将当前仅具备高保真静态外壳和模拟图片返回的页面，升级为一个可直接配置并投入使用的 GPT Image-2 对话式图像工作台。

设计目标如下：

- 使用 OpenAI 兼容的 OpenRouter 中转站接入方式。
- 采用纯前端直连 `.env` 的配置模式，不引入本地代理层。
- 保持高端、克制、紧凑、中文化的深色工作台视觉。
- 不是一次性生图面板，而是支持多轮上下文续聊的图像会话产品。
- 支持开箱即用的默认配置、错误提示、历史持久化和图像继续编辑。

## 2. 范围

### 2.1 第一版必须完成

- OpenAI 兼容中转站真实接入。
- `.env` 默认配置与前端本地覆盖。
- 多主题图像会话。
- 多轮图像续聊。
- 图片消息卡片动作。
- 本地持久化。
- 完整空状态、加载态、错误态。
- 高质感工作台 UI。

### 2.2 第一版建议完成

- 参考图上传。
- 主题自动命名。
- 图片预览大图层。
- 一键重试。
- 复制提示词。

### 2.3 第一版暂不纳入

- 用户登录。
- 云端同步。
- 团队协作。
- 局部涂抹重绘。
- 复杂图层编辑。
- 服务端代理。
- 计费与额度系统。

## 3. 产品定位

本产品不是传统绘图后台，也不是只会发 prompt 的单轮图片生成器。

产品定位为：

- 外观上保持类似 ChatGPT 的高集成、单列主工作区体验。
- 交互上以聊天流承载图像生成和图像修改。
- 能力上具备图像工作台的多轮演进、复用、重试和参考图机制。

推荐采用工作台型布局，而不是单栏极简型或双态混合型。

采用该布局的原因：

- 最符合“跟 gpt-image-2 聊天”的产品语义。
- 主题历史、图像卡片动作和多轮上下文更自然。
- 在功能完整的前提下，仍能维持视觉上的紧凑和专业感。

## 4. 界面结构

页面拆分为 5 个核心区域。

### 4.1 左侧主题栏

包含以下内容：

- 新建创作入口。
- 搜索历史主题。
- 主题列表。
- 每个主题显示标题、最近时间、最新缩略图、当前状态。

主题状态仅保留：

- `idle`
- `generating`
- `error`

### 4.2 顶部会话头部

显示以下信息与动作：

- 当前主题名。
- 当前模型名。
- 中转站连接状态。
- 主题重命名。
- 清空当前会话。
- 导出提示词。

### 4.3 中部消息流

消息流是整个产品的主承载区。

需要支持：

- 用户创作提示词。
- 用户继续修改指令。
- AI 返回的图片结果卡片。
- AI 返回的补充说明。
- 处理中与失败状态消息。

### 4.4 底部输入控制台

保持高集成输入结构，不额外拆出一条专业参数侧栏。

主控制区包含：

- 多行输入框。
- 模型选择。
- 尺寸选择。
- 数量选择。
- 参考图入口。
- 发送按钮。

高级设置抽屉包含：

- 质量。
- 背景设置。
- 输出格式。
- 自定义 baseURL。
- 自定义 API Key。
- 请求模式。
- 超时时间。

### 4.5 不新增独立右侧栏

第一版不增加单独的右侧参数栏。

原因：

- 保持你偏好的高集成单列结构。
- 避免做成传统绘图平台那种满屏分栏工具后台。
- 让图像编辑能力通过图片卡片动作和输入区弹层承载。

## 5. 数据结构设计

现有 `topics + messages + config` 结构需升级为 4 层状态。

### 5.1 appConfig

用于存储全局配置：

- `baseURL`
- `apiKey`
- `defaultModel`
- `defaultSize`
- `defaultQuality`
- `defaultN`
- `timeout`
- `requestMode`

配置来源优先级：

- `.env` 默认值
- 本地设置面板覆盖值

### 5.2 topic

一个主题代表一条图像创作会话。

建议字段：

```js
const topic = {
  id: 'string',
  title: 'string',
  coverImage: 'string|null',
  lastPrompt: 'string',
  updatedAt: 0,
  messageCount: 0,
  status: 'idle|generating|error'
}
```

### 5.3 message

消息必须做成强类型消息，不再仅使用 `text|image` 二元结构。

建议支持以下类型：

- `user_prompt`
- `assistant_images`
- `assistant_text`
- `system_status`

其中 `assistant_images` 结构建议如下：

```js
const assistantImagesMessage = {
  id: 'string',
  topicId: 'string',
  type: 'assistant_images',
  role: 'assistant',
  prompt: 'string',
  revisedPrompt: 'string',
  images: [
    {
      id: 'string',
      url: 'string',
      width: 1024,
      height: 1024
    }
  ],
  model: 'gpt-image-2',
  size: '1024x1024',
  quality: 'high',
  n: 1,
  seed: 'string|null',
  sourceMessageId: 'string|null',
  createdAt: 0
}
```

这样可支持：

- 基于上一轮图片继续创作。
- 生成变体。
- 复用同轮参数再次生成。
- 保留会话演进链路。

### 5.4 draftState

当前输入草稿单独存储，不直接写入历史消息。

建议字段：

```js
const draftState = {
  prompt: '',
  model: 'gpt-image-2',
  size: '1024x1024',
  quality: 'high',
  n: 1,
  referenceImages: []
}
```

这样可保证切换主题时草稿隔离，避免不同主题互相污染。

## 6. 请求链路设计

### 6.1 文本提交到图像生成

基础流程如下：

1. 用户提交输入框内容。
2. 前端立即插入一条 `user_prompt` 消息。
3. 前端再插入一条 `system_status(generating)` 消息。
4. 请求发送至 OpenAI 兼容中转站。
5. 成功时，用 `assistant_images` 替换生成中状态。
6. 失败时，用 `assistant_text` 或错误卡片替换生成中状态。

### 6.2 基于已有图片继续聊

流程如下：

1. 用户点击某张图片的继续细化或设为参考图。
2. 前端将对应图片写入 `draftState.referenceImages`。
3. 用户输入新的修改指令。
4. 请求中同时附带文本指令和参考图。
5. 返回结果通过 `sourceMessageId` 关联上一轮图像消息。

### 6.3 设计原则

- UI 始终表现为聊天工作流。
- 底层请求能力可适配不同 OpenAI 兼容中转站。
- 消息流必须可回溯，不能丢失图像来源关系。

## 7. 接口适配策略

由于目标中转站为 OpenAI 兼容协议，前端需要引入独立适配层，禁止把请求逻辑直接写在页面组件内。

建议新增以下模块：

- `src/services/aiClient.js`
- `src/services/imageSession.js`
- `src/utils/normalize.js`

职责划分如下：

### 7.1 aiClient

负责：

- 创建基础请求实例。
- 注入鉴权头。
- 处理超时。
- 处理公共错误归一化。

### 7.2 imageSession

负责：

- 文本生成图片。
- 基于参考图继续编辑。
- 生成变体。
- 再次生成。

### 7.3 normalize

负责：

- 将不同中转站返回结构归一化为前端统一消息格式。
- 统一适配 `url`、`b64_json`、文本说明和错误体。

## 8. 请求模式

内部支持两种请求模式，但普通用户默认只感知一种稳定体验。

### 8.1 聊天封装模式

- 优先走 `/chat/completions`
- 用于兼容某些将图像能力包装成消息式返回的中转站

### 8.2 图片生成模式

- 走 `/images/generations` 或兼容图像接口
- 更贴近图像模型原生能力
- 通常更稳定

### 8.3 默认策略

- 前端内部同时支持两种模式。
- 默认启用图片生成模式。
- 协议切换仅放在高级设置中。
- 主界面不暴露底层协议细节。

## 9. 开箱即用配置

项目应提供完整的 `.env.example`，复制为 `.env.local` 后即可启动。

建议内容如下：

```bash
VITE_AI_BASE_URL=https://your-proxy.example.com/v1
VITE_AI_API_KEY=your-api-key
VITE_AI_MODEL=gpt-image-2
VITE_AI_MODE=openai-image
VITE_AI_DEFAULT_SIZE=1024x1024
VITE_AI_DEFAULT_QUALITY=high
VITE_AI_DEFAULT_N=1
VITE_AI_TIMEOUT=120000
```

配置规则如下：

- `.env` 作为默认启动配置。
- UI 中的设置面板可以对默认值做本地覆盖。
- 用户可一键恢复默认配置。
- 若缺少 `baseURL` 或 `apiKey`，首屏必须进入配置引导状态。

## 10. 主界面配置暴露原则

### 10.1 主界面直接可见

- 模型
- 尺寸
- 张数
- 参考图
- 发送

### 10.2 高级设置中显示

- 质量
- 背景
- 输出格式
- 超时时间
- 请求模式
- 自定义 baseURL
- 自定义 API Key

### 10.3 不对普通用户直接暴露

- 原始请求头编辑
- 底层协议细节
- 低价值实验参数

原则：

- 保持产品感，而不是调试后台感。
- 主界面必须简洁直接。
- 把复杂度压进高级设置，而不是压到首页。

## 11. 状态体验设计

至少支持以下 5 种核心状态。

### 11.1 未配置

- 缺少 `baseURL` 或 `apiKey`
- 发送动作触发设置抽屉，而不是直接报错
- 空状态明确提示需要完成连接配置

### 11.2 生成中

- 消息流插入处理中消息
- 展示模型、尺寸、张数和已耗时
- 输入区允许继续编辑草稿
- 当前主题禁止并发提交第二次生成

### 11.3 生成成功

- 用图片消息替换处理中消息
- 自动更新主题封面
- 自动更新主题最近时间
- 可根据首轮提示词建议主题标题

### 11.4 生成失败

- 错误必须以消息卡片出现在会话流中
- 提供“重试本次参数”和“复制错误详情”动作
- 顶部连接状态同步切为连接异常

### 11.5 部分成功

- 部分图片成功时保留成功结果
- 消息卡片显示“部分完成”
- 禁止整批直接视为完全失败

## 12. 图片卡片动作设计

每个 `assistant_images` 消息卡片第一版至少支持以下动作：

### 12.1 继续细化

- 将当前图片加入参考图
- 自动聚焦输入框
- 草稿区显示“基于这张图继续创作”

### 12.2 生成变体

- 复用上一轮提示词和参数
- 允许补充一句额外要求

### 12.3 再次生成

- 完全复用该轮参数重新出图

### 12.4 设为参考图

- 将某张结果图挂入当前草稿参考区

### 12.5 下载原图

- 直接下载
- 文件名带主题名、模型名和时间戳

### 12.6 建议补充动作

- 复制提示词

该动作优先级略低于前五项，但第一版若有余力应一并纳入。

## 13. 历史持久化设计

第一版采用浏览器本地持久化，不依赖后端。

### 13.1 持久化内容

- 主题列表
- 消息历史
- 当前草稿
- UI 设置
- 最近使用模型和尺寸
- 最近参考图记录

### 13.2 技术策略

- Pinia 状态变化后写入 `localStorage`
- 启动时自动恢复状态
- 引入简单版本号用于后续结构迁移

### 13.3 清理能力

需要提供：

- 清空当前主题
- 清空全部本地数据

其中清空全部数据必须有二次确认。

## 14. UI 风格要求

必须延续并提升当前项目已有的深色赛博工作台风格。

要求如下：

- 界面语言必须使用中文。
- 保持紧凑布局，不做松散留白。
- 强调高端、克制、专业，不做廉价 Demo 感。
- 使用深色背景、弱边框、微光、毛玻璃和环境发光。
- 侧边栏保持单列高集成结构。
- 输入控制台和图片卡片要有明确层级和光感。

## 16. 验收标准

第一版完成后，应满足以下标准：

- 复制 `.env.example` 为 `.env.local` 后即可启动并发起真实请求。
- 用户可以创建多个主题并保留各自消息历史。
- 用户可以基于任意一张已有图片继续修改创作。
- 请求异常时，用户能在界面上看到明确错误和可执行动作。
- 刷新页面后历史记录、配置和草稿可恢复。
- 产品体验像成熟 AI 对话工作台，而不是静态展示壳子。

## 17. 风险与约束

- 不同 OpenAI 兼容中转站对图像接口支持度可能不完全一致。
- 部分中转站可能返回 `b64_json`，需要前端额外归一化处理。
- 纯前端直连方案存在密钥暴露风险，但该方案已由需求确认接受。
- 若后续要接入真正的局部重绘或服务端能力，需要额外规划第二阶段架构。

## 18. 最终结论

本项目第一阶段应围绕“GPT Image-2 对话式图像工作台”展开，而不是继续停留在展示型高保真前端。

实现重点不是简单接通一条生图 API，而是同时完成以下四件事：

- 接入真实可用的 OpenAI 兼容中转站。
- 构建支持多轮续聊的消息和图片引用结构。
- 提供开箱即用的配置、状态反馈和本地持久化。
- 在视觉上延续高端、克制、专业的中文 AI 工作台体验。
