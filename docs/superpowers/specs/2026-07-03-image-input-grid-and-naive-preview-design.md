# 输入区尺寸网格、多图上传与 Naive 图片预览设计文档

## 1. 目标

在现有 GPT Image-2 对话式图像工作台基础上，进一步把输入区做成接近专业创作工作台的形态，并补齐图生图入口和统一的图片预览方式。

本次增量设计目标如下：

- 尺寸选择不再使用普通下拉，而是改成参考图风格的深色网格弹层。
- 输入框内部支持图生图上传，且支持一次上传多张参考图。
- 明确提示上传上限，并按 OpenRouter 当前能力限制为最多 16 张。
- 历史生成图与本地上传图都统一进入 `referenceImages` 链路。
- 全局查看图片切换为 Naive UI 图片组件方案，不再继续维护自定义预览弹窗。

## 2. 范围

### 2.1 必须完成

- 尺寸触发器与网格弹层。
- 输入框内底栏上传入口。
- 多图上传与多图删除。
- 上传数量限制提示。
- 历史生成图与本地上传图统一映射到 `input_references`。
- 消息图片改为 Naive UI 的 `n-image` / `n-image-group`。
- 废弃自定义图片预览主路径。

### 2.2 建议完成

- 参考图缩略图横向滚动。
- 上传区显示“最多 16 张参考图”。
- 尺寸卡片显示比例和值两行信息。
- 全屏输入态下保留上传区和尺寸弹层。

### 2.3 暂不纳入

- 图片拖拽排序。
- 图片裁切与局部编辑。
- 独立的参考图库。
- 参考图服务端持久化。

## 3. 产品定位

本次增量的目标不是单独增加几个控件，而是把输入区从“普通文本框 + 参数行”升级为“高集成图像创作控制台”。

定位原则如下：

- 输入、参数和参考图必须处于同一块工作台中，不拆成零散面板。
- 尺寸选择要具备“扫一眼即可判断”的能力，而不是下拉里慢慢读。
- 图生图上传必须足够近，不应把上传功能藏进设置抽屉。
- 全局看图必须统一走 Naive UI 图片组件，避免双套预览体系并存。

## 4. 核心方案

建议采用“输入区工作台化 + 参考图内嵌 + Naive 图片预览统一化”的组合方案。

### 4.1 输入区工作台化

输入区分为四层：

- 主输入编辑区
- 参考图缩略图区
- 底部工具栏
- 尺寸网格弹层

这样可以保证用户在同一视觉区域内完成：

- 输入提示词
- 选择尺寸
- 上传参考图
- 发送请求

### 4.2 参考图统一数据链路

参考图不再区分“历史生成图”和“本地上传图”的 UI 处理路径，而是统一进入 `referenceImages`。

所有参考图都应具备：

- 预览地址
- 原始数据地址或可发送值
- 唯一标识
- 可删除能力

### 4.3 Naive UI 图片预览统一化

图片展示和全局预览改为 Naive UI 原生能力：

- 单图使用 `n-image`
- 多图批次使用 `n-image-group`

这样可以直接使用 Naive UI 提供的预览遮罩层、切换和查看体验，不再维护一套自定义的图片预览弹层。

## 5. 输入区结构设计

### 5.1 主输入编辑区

主输入编辑区保留大文本输入框，并继续支持全屏展开。

要求如下：

- 默认态用于快速输入提示词。
- 全屏态用于长提示词和多图图生图场景。
- 全屏态时，底部工具栏、上传区、尺寸弹层都仍然位于同一块输入面板中。

### 5.2 参考图区

参考图区位于输入框内部，靠近底栏上方。

要求如下：

- 未上传时不显示缩略图区。
- 上传后按卡片展示每张参考图。
- 每张参考图带删除按钮。
- 多张时横向滚动，不撑破输入框整体高度。
- 对于来自历史消息的参考图，也按同一缩略图卡片风格展示。

### 5.3 底部工具栏

底栏左侧建议包含：

- 图片上传入口
- 尺寸触发器
- 后续参数入口预留位

底栏右侧建议包含：

- 连接状态
- 发送按钮

布局原则如下：

- 尽量靠近参考图中的工作台质感。
- 所有高频动作都在首屏可见范围内。
- 不使用原生表单控件。

## 6. 尺寸网格弹层设计

### 6.1 触发方式

点击底栏中的“尺寸”触发器后，弹出深色网格面板。

当前选中值在触发器中展示：

- `auto`
- 或 `比例 + 像素值`

### 6.2 网格结构

建议将尺寸分为三组展示：

#### 自动

- `auto`

#### 常用

- `1:1 · 1024×1024`
- `1:1 · 1536×1536`
- `3:2 · 1536×1024`
- `2:3 · 1024×1536`
- `16:9 · 1536×864`
- `9:16 · 864×1536`

#### 扩展

- `4:3 · 1536×1152`
- `3:4 · 1152×1536`
- `2:1 · 1536×768`
- `1:2 · 768×1536`
- `21:9 · 1792×768`
- `9:21 · 768×1792`

### 6.3 视觉规则

每个尺寸项为一个小卡片，而不是菜单项。

卡片内容建议如下：

- 第一行：比例
- 第二行：像素值

交互规则：

- 当前选中项高亮
- `auto` 作为首位默认项
- 面板风格保持深色、克制、低噪点

## 7. 图生图上传设计

### 7.1 上传入口

上传入口位于输入框底栏左侧，名称可直接使用：

- `图片`

点击后打开系统文件选择器。

### 7.2 上传规则

上传规则建议如下：

- 支持多图上传
- 支持格式：`png`、`jpg`、`jpeg`、`webp`
- 最多上传 `16` 张
- 超出限制时阻止新增并提示

提示文案建议：

- `最多上传 16 张参考图`

### 7.3 缩略图表现

每张上传图展示：

- 缩略图
- 文件名或序号
- 删除按钮

若当前已有历史参考图和本地上传图混用，仍统一放在同一个缩略图区中展示。

## 8. 数据结构设计

当前 `referenceImages` 需要从简单 `url` 数组升级为结构化对象数组。

建议结构如下：

```js
{
  id: 'ref-1',
  name: 'scene-01.png',
  type: 'image/png',
  url: 'blob:...',
  dataUrl: 'data:image/png;base64,...',
  sourceMessageId: null
}
```

字段说明如下：

- `id`：本地唯一标识
- `name`：文件名或生成图标识
- `type`：文件类型
- `url`：浏览器展示用地址
- `dataUrl`：用于发送给 OpenRouter 的可序列化数据
- `sourceMessageId`：若来自历史生成图，则记录来源消息

## 9. 请求链路设计

### 9.1 OpenRouter 映射

当前请求层已经支持：

- `draft.referenceImages`
- `payload.input_references`

本次需要升级映射逻辑，统一优先发送可直接使用的数据地址。

建议逻辑如下：

```js
payload.input_references = draft.referenceImages.map((item) => {
  return item.dataUrl || item.url
})
```

### 9.2 来源兼容

对不同来源的参考图，映射规则如下：

- 本地上传图：优先使用 `dataUrl`
- 历史生成图：优先使用 `dataUrl`，若无则回退 `url`

这样可以确保：

- 本地上传图不依赖外部地址可访问
- 历史生成图继续细化时复用同一链路

## 10. 图片展示与全局预览

### 10.1 主路径

图片展示和全局查看统一改为 Naive UI 图片组件。

建议方式如下：

- 图片卡片内单图使用 `n-image`
- 同一批次图片包在 `n-image-group` 中

### 10.2 预览行为

点击任意图片后，进入 Naive UI 的内建预览。

原则如下：

- 不再使用自定义 `ImagePreviewModal.vue` 作为主预览方案
- 图片预览交互交给 Naive UI 负责
- 业务动作如“下载原图”“继续细化”“设为参考图”仍保留在消息卡片动作区

### 10.3 迁移策略

迁移时建议：

- 先把消息图片切换到 `n-image` / `n-image-group`
- 再移除 `ChatArea` 对自定义图片预览弹层的依赖
- 最后下线 `ImagePreviewModal.vue`

## 12. 错误处理

### 12.1 上传超限

- 阻止继续添加
- 显示 `最多上传 16 张参考图`

### 12.2 文件类型不支持

- 拒绝加入参考图区
- 显示简洁错误提示

### 12.3 参考图删除

- 删除单张只影响该图片
- 不影响其他已上传图片和当前提示词内容

### 12.4 Naive 预览替换期间

- 若切换到 `n-image-group` 后某张图失败，仍允许用户使用消息卡片里的下载和继续细化动作

## 13. 测试策略

至少覆盖以下行为：

- 尺寸触发器可打开网格弹层。
- 尺寸列表包含 `auto` 与常见比例。
- 上传多图后参考图区正确显示。
- 超过 16 张时阻止继续上传。
- 删除单张参考图只移除对应项。
- `input_references` 正确映射为 `dataUrl || url`。
- 图片卡片使用 Naive UI 图片组件而不是自定义预览弹层。

## 14. 验收标准

本次增量完成后，应满足以下标准：

- 尺寸选择改为深色网格弹层。
- 尺寸列表包含 `auto` 和完整常见比例。
- 输入框内支持多图上传和多图删除。
- 明确提示最多上传 16 张参考图。
- 历史生成图和本地上传图都可作为参考图继续图生图。
- 图片全局查看使用 Naive UI 图片组件方案，不再依赖自定义预览弹层。

## 15. 风险与约束

- 多图上传会让输入区高度和布局复杂度提升，因此必须控制缩略图区的滚动方式。
- `dataUrl` 体积较大，上传多张大图时会增加本地状态与请求体压力。
- Naive UI 预览能力足够稳定，但可定制度不如自定义弹层，因此业务动作应保留在消息卡片层而非预览层。

## 16. 最终结论

本次增量应采用“尺寸网格弹层 + 输入框内多图上传 + 参考图统一链路 + Naive UI 图片预览”的组合方案。

该方案同时满足以下目标：

- 让尺寸选择更接近专业图像工作台。
- 让图生图在输入区内完成闭环，不需要跳出当前工作流。
- 让本地上传图和历史生成图共用一套参考图机制。
- 让图片查看统一落到 Naive UI 组件能力上，减少重复维护。
